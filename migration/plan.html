05 D1 schema — a proper relational design

Base44's nine entities are JSON-schema documents with embedded arrays (options[], payments[], collection_ids[]). None of that is reproduced structurally. Every embedded array becomes a real child table with a foreign key; every money field becomes an integer count of pence, not a float; every list Base44 let float free (shipping methods, settings) gets a table instead of a singleton blob.

Deliberate departures from the Base44 shape

  • Money as integer pence (price_cents, not price: 45.00) — eliminates float rounding drift through the pricing chain in §08, and is what Stripe's API expects anyway.
  • Base44 ids kept verbatim as D1 TEXT primary keys on import. They're already opaque 24-hex strings referenced across every relationship in the export — remapping them would be pure risk for no benefit.
  • product.collection_ids[] → join table product_collections.
  • product.options[].values[], customizations[], images[] → child tables with product_id FK and a sort_order column (array order was meaningful and silent in Base44; now explicit).
  • order.payments[], order.internal_notes[] → order_payments, order_notes tables — an audit trail admins can query, instead of a JSON blob rewritten wholesale on every update.
  • StoreSettings.shipping_methods[] → shipping_methods table; settings becomes a real singleton via a CHECK (id = 1) row instead of "first record returned by list()".
  • Slug uniqueness and discount code uniqueness are UNIQUE constraints, not application-level hope.
  • An is_sample, created_by_id Base44 built-ins are dropped — the first is meaningless outside Base44, the second is replaced by a real created_by FK only where it's actually used.

06 R2 media

At handover, zero records reference media.base44.com — only three branding constants and the favicon need re-hosting. Product/category/collection seed images are Unsplash hotlinks and are left as-is.

  • Key scheme: products/<productId>/<n>.<ext>, bespoke/<requestId>/<n>.<ext>, branding/<name>.<ext>.
  • Upload path: Worker-mediated, not presigned — the browser POSTs multipart/form-data to /api/media; the Worker validates mime type and a 10 MB cap, writes via the R2 binding, inserts a media_assets row, and returns the public URL. No S3-compatible credentials needed, and uploads are now attributable and deletable (Base44 tracked neither).
  • Access: public bucket served from a custom subdomain (e.g. media.auroracreations.co.uk) with Cloudflare's edge cache in front; private bucket served only through an authenticated Worker route.
  • Migration: download the three branding assets from media.base44.com while Base44 is still live, re-upload to the public bucket, update src/config/brand.js and the index.html favicon.

Decision D — confirmed

Image delivery: plain R2 + custom domain

The current ui/image.jsx requests server-resized WebP variants from Base44/Wix; that's not replicated. Plain R2 serves originals from a custom domain — no responsive variants unless reimplemented later. Catalogue is 8 products; optimisation isn't the bottleneck yet. Revisit Cloudflare Images if the catalogue or traffic grows.

07 Authentication

Base44 owned password hashes, OAuth links and OTP state — none of it is exportable. Every user account is re-created with no password and must reset via email.

  • Password auth: WebCrypto PBKDF2 (Workers-native, no npm dependency needs a Node polyfill) hashing into the users table.
  • Sessions: opaque random token, SHA-256 hash stored in the sessions table, HttpOnly + Secure + SameSite=Lax cookie — not a bearer token in localStorage like today.
  • Google OAuth: standard authorization-code flow implemented directly in the Worker against Aurora's own Google OAuth client (Base44's was shared platform-wide and goes away with it).
  • Error codes: the adapter must keep throwing { code: 'auth_required' | 'user_not_registered' | 'unknown' } — AuthContext.jsx, ProtectedRoute and UserNotRegisteredError depend on those exact codes and need no changes otherwise.
  • Admin gate: a Worker middleware resolves the session → user → role once per request and rejects before any handler runs — closing the SDK-is-open-to-anyone gap noted in HANDOVER.md §10.1.

Decision B

Roll a lightweight custom auth layer, or bring in a library?

Aurora's auth surface is small and fully specified by API_CONTRACT.md (password, Google, OTP-verify, reset). A custom implementation is ~300 lines of Worker code with zero framework lock-in and matches error codes exactly. A library (Auth.js, etc.) trades that control for less code to own, at the cost of adapting its session/error model to what AuthContext.jsx already expects.

Recommendation: custom, Workers-native (WebCrypto + D1 sessions). Small enough surface that "own it outright" beats "adapt a library's opinions."

08 Server-side pricing

A single pure module, pricing.server.js, reproduces SERVER_REQUIREMENTS.md exactly — same formulas, same rounding, same edge cases (including the sale_price quirk: it's used whenever set, even if higher than price, unless deliberately fixed). It is the only place order totals are computed, called from two routes:

  1. POST /api/orders — client sends cart intent only (product ids, quantities, selected option/customisation labels, discount code). The Worker re-reads current product rows, recomputes unit_total → line_total → subtotal → discount → tax → shipping → total → dueNow, and persists that, not whatever the client sent.
  2. POST /api/discounts/validate — same five-rule cascade as today (API_CONTRACT.md), now server-side; usage_count increments atomically inside the order-creation transaction rather than via a separate client call to markUsed.

Stock is checked in the same transaction: availability = 'out_of_stock' or stock_quantity ≤ 0 on a stock-controlled item rejects the order before any PaymentIntent is created.

09 Stripe

Nothing exists today beyond an unused npm dependency. Built from the "intended design" already sketched in STRIPE.md, using stripe-node's fetch-based HTTP client (Workers-compatible, no Node http dependency).

  • Order creation computes dueNow server-side (§08) and creates a PaymentIntent for that amount in pence; orders with requires_approval (non-immediate special requests) skip payment entirely, matching today's behaviour.
  • Checkout step 3 mounts Stripe's Payment Element with the returned client_secret — the one piece of the diagram in §03 where the browser talks to Stripe directly, and never sees or sends an amount.
  • POST /api/webhooks/stripe verifies the signature, checks the event id against stripe_events for idempotency, then on payment_intent.succeeded: appends an order_payments row, updates amount_paid/balance_due/payment_status, sets production_status = 'confirmed', and decrements stock.
  • Admin "record a manual payment" and "request balance" become real server mutations against the same tables, with an audit trail via order_payments instead of a client-computed rewrite of the whole array.
  • Refunds go through the Stripe API from an admin route, writing a refund-type order_payments row.

10 Order processing & inventory

  • Order numbers generated server-side — a counters table with an atomic UPDATE … RETURNING, formatted as today's AUR-<base36> for continuity, but guaranteed unique under concurrency (the current Date.now().toString(36) is not).
  • Inventory decrements on payment_intent.succeeded, not at checkout — an abandoned or failed payment never touches stock.
  • getBySlug filters status = 'published' on the public storefront route, closing the draft-product-reachable-by-URL gap.
  • Admin CRUD for products/orders/bespoke/settings/discounts all require role = 'admin', enforced in Worker middleware, not just the React AdminLayout check.

11 Data & media migration

migration/export/*.json is the source: 8 products, 7 categories, 3 collections, 1 discount code, 1 settings record, 2 users, zero orders/bespoke requests/newsletter subscribers.

  1. Categories, collections (no dependencies).
  2. Products + child rows (options, customisations, images, deposit, special-request) — ids kept verbatim from the export.
  3. Discount codes, store settings (+ derived shipping_methods rows), newsletter subscribers.
  4. Users — imported with password_hash = NULL and a forced must_reset_password flag; each gets a password-reset email once the mailer (§14) is live. role carried over as-is.
  5. Orders, bespoke requests — moot at handover time (zero records) but the importer handles them for a later re-export closer to cut-over, per EXPORT.md's recommended re-export step.

Since nothing currently references media.base44.com, the only media migration required is the three branding assets + favicon (§06). Re-run /admin/export immediately before cut-over in case content was added after this handover commit, and re-check for any new media.base44.com URLs at that point.
